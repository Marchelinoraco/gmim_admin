Langganan & Billing

Mesin langganan agar produk benar-benar SaaS: paket, status, tagihan, middleware penegak expiry, dan halaman billing. Dibangun sejak awal.

⚠️ Dua Konteks Midtrans yang BERBEDA

Persembahan jemaat

Akun Midtrans gereja → dana ke rekening gereja. Diatur Bendahara (AD-8).

Pembayaran langganan

Akun Midtrans platform → dana ke rekening operator. Diatur modul billing (AD-11).

Gereja bayar langganan ke platform; jemaat memberi persembahan ke gereja. Akun & tujuan dana berbeda.

Penegakan Expiry — EnsureSubscriptionActive

1. Ambil langganan gereja aktif.
2. Hitung status efektif (trial_berakhir/berakhir vs hari ini, + grace).
3. Jika expired/canceled:
     - izinkan HANYA rute billing + read-only (GET);
     - tolak semua mutasi (POST/PUT/DELETE) -> 402 Payment Required.
4. Jika past_due: lanjut + flag agar FE tampilkan banner.

Job harian langganan:evaluasi memutakhirkan status + kirim email pengingat (H-7/H-1/H+1).

Alur Pembayaran (Midtrans platform)

sequenceDiagram
    autonumber
    actor A as Admin Gereja
    participant FE as billing (gmim_manage)
    participant API as gmim_api (billing)
    participant M as Midtrans (platform)
    A->>FE: pilih paket / perpanjang
    FE->>API: POST /langganan/checkout
    API->>API: buat tagihan (unpaid)
    API->>M: minta Snap token (server_key platform)
    M-->>API: snap_token
    API-->>FE: { snap_token }
    A->>M: bayar via Snap
    M-->>API: webhook notifikasi
    API->>API: verifikasi signature + idempoten
    API->>API: tagihan=paid, langganan=active, perpanjang berakhir
    API-->>FE: status terbaru

Skema Data (di gmim_api)

paket

katalog: nama, harga bulanan/tahunan, batas (json)

langganan

per gereja (1-1): status, siklus, trial_berakhir, berakhir

tagihan

invoice: nomor, periode, jumlah, status, jatuh_tempo, midtrans_order_id

Sumber kebenaran langganan = tabel langganan; gereja.status_langganan hanya cache tampilan.
