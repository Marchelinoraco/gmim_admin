SSO & Identitas Terpusat

🟣 STATUS: DITUNDA (Keputusan Final KF-2). SSO sebagai service terpisah (gmim_sso) tidak dibangun sekarang. Untuk MVP, identitas = modul di gmim_api (Sanctum + email unik global), URL path-based /g/<slug> — "tanpa duplikasi user" sudah tercapai dari satu tabel church_users ber-email unik. Halaman ini = blueprint ekstraksi masa depan saat skala menuntut.

Rancangan target (saat diekstrak): backend identitas terpisah sebagai sumber tunggal akun; login lewat SSO; gmim_api memvalidasi token; tiap user terkunci satu gereja.

🆔

Satu identitas

Satu tabel users di SSO → tidak ada duplikasi user antar tenant.

🚪

Satu pintu login

Login dari domain utama → SSO autentikasi → kirim token ke backend utama.

🔐

Password terpusat

gmim_api tak pernah simpan password — hanya di SSO.

⛓️

Terkunci 1 gereja

Token membawa gereja_id; akses subdomain lain ditolak.

Token (JWT access)

Ditandatangani kunci privat SSO (RS256), divalidasi gmim_api via JWKS. Dua klaim kunci menegakkan keamanan:

{
  "iss": "https://sso.gmim-keuangan.id",
  "sub": "usr_01HX...",        // identitas tunggal → anti-duplikasi
  "email": "bendahara@bethesda.id",
  "gereja_id": "g-001",        // PENGIKAT: token hanya untuk gereja ini
  "aud": "bethesda",
  "role": "bendahara",
  "iat": 1735900000,
  "exp": 1735900900             // pendek (±15 menit) + refresh token di SSO
}

Penegakan "1 user → 1 gereja"

1SSO menerbitkan token dengan gereja_id dari user_gereja (MVP: satu-satunya gerejanya).
2gmim_api VerifySsoToken menolak 403 bila gereja_id token ≠ subdomain diakses.
3Global Scope membatasi semua query ke gereja_id itu (lihat Bagian 05).
Token gereja A dipakai ke subdomain gereja B → ditolak di langkah 2. Backend lupa filter → diamankan langkah 3. Berlapis.

Migrasi dari Sanctum

  1. 1. Bangun gmim_sso (Laravel + Passport) + tabel users.
  2. 2. Pindahkan identitas tiap church_users → SSO users (email + hash, atau undangan set-password).
  3. 3. Tambah church_users.sso_user_id; isi pemetaan; hapus kolom password.
  4. 4. Ganti auth:sanctum → VerifySsoToken di gmim_api.
  5. 5. Ganti login FE → alur OIDC (redirect SSO → exchange code → JWT).
  6. 6. Dual-run saat transisi, lalu cutover.

Keputusan Terbuka (SSO)

Protokol: OIDC/Passport penuh (rekomendasi) vs JWT ringan buatan sendiri.
Peran di token: resolve di gmim_api (rekomendasi) vs embed klaim.
Domain SSO: sso. terpisah vs menyatu dengan app.
Multi-gereja per user: kunci 1:1 (MVP) vs pemilih gereja.
